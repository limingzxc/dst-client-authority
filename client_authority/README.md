# Client Authority / 客户端权威移动（实验性）

把 DST 的移动改成「客户端计算 + 服务端校验」。**双端模组**，服务器和所有客户端都必须装。

## 服务端是怎么纠正你的

原版有三层，一层比一层狠：

| 层 | 机制 | 原版行为 | 本模组 |
| --- | --- | --- | --- |
| 一 | `CanLocomote()` 返回 false | 客户端整段停止预测，输入延迟退回一个 RTT | 拆掉闸门，永远返回 true |
| 二 | `RemotePausePrediction(frames)` | 服务端主动喊停，客户端冻结 N 帧 | 覆盖 `PlayerController:RemotePausePrediction` |
| 三 | 位置 netvar 覆盖 | 服务端算出的位置直接盖掉客户端的 | 让服务端先对齐到客户端，覆盖变成空操作 |

**第三层关不掉。** 位置同步在引擎里，Lua 没有钩子。但可以让它变成恒等变换：服务端上报的位置本来就等于客户端的位置，那"纠正"就等于什么都没做。

这就是为什么必须三层一起上。只拆前两层，客户端会和服务端越走越远，最后一次性大回弹；只做第三层，闸门还在，客户端还是会在砍树时停止预测。

## 它做的事

```
客户端 30Hz 上报 (seq, x, y, z)
        │
        ├─ 序列号不新？        丢弃
        ├─ 静默窗口内？        丢弃
        ├─ 船 / 平台 / nopredict？ 不采纳
        └─ 位移 ≤ 速度×间隔×倍数？  采纳，把服务端位置对齐过去
                                  否则丢弃，服务端位置不动
```

服务端**不停止**自己的 `locomotor`。它继续模拟、继续驱动状态机，所以动画、碰撞、怪物 AI 都还是原版的。区别只在于每帧结束前，位置会被对齐到客户端上报的那个点。

因为服务端本来就在朝同一个方向走，这个对齐量通常很小；而客户端收到的权威位置因此接近自己的预测值，就不会再触发回滚。

## 对齐 Minecraft 的四处

MC 的 `handleMovePlayer` 不是"一个固定阈值"，是四件事配合。这里逐条对应：

| MC 的做法 | 本模组 |
| --- | --- |
| `awaitingPositionFromClient`：传送后旧包一律作废，等客户端确认 | 检测服务端位置突变且状态机不在 `moving`，开 0.35 秒静默窗口，期间丢弃上报 |
| `expectedMoveDist = 移动速度 × 实际经过的 tick 数` | 阈值 = `locomotor 速度 × 实际包间隔 × 宽容倍数`，间隔夹在 16–100ms 之间 |
| TCP 保证顺序，服务端仍按 `lastGood` 推进 | 包带单调递增序列号，`seq <= last` 直接丢 |
| `movedWronglyDist` 累计，超限踢人 | 连续被拒累计，超阈值打日志（朋友服不踢人） |

**为什么阈值要按时间算，而不是固定每包距离。** 固定 0.4 格/包隐含假设包间隔 33ms。客户端掉到 20fps，间隔变 50ms，一帧位移 0.5 格就被判成作弊——越卡的机器越容易被拒，越拒越卡。按时间算就没有这个问题，但必须夹住上限，否则长时间不发包能攒出一次瞬移额度。

**为什么传送要单独处理。** 传送那一瞬间，在途的旧包还在路上。服务端如果照常校验，会把玩家从新位置拽回旧位置。MC 的解法是让所有旧包失效，这里用"位置突变 + 不在 moving"作为触发条件，不需要知道是虫洞还是传送法杖。

## 安装

1. `client_authority` 放进服务器的 `mods/`，并在 `modoverrides.lua` 里启用。
2. 同一个文件夹发给每个客户端，放进各自的 `mods/`。
3. 双端都要启用。服务器没装、客户端装了，进不去。

## 三条真实代价

**一、开了「客户端始终预测」之后，可以在砍树、攻击时移动。**
原版 `busy` 状态会锁住移动，这是设计。拆掉闸门后你会边砍边滑。这不是 bug，是这次改动的直接后果。不想要就把这一项关掉，但那样「原地走路」大概率还在。

**二、服务端的碰撞不再是权威。**
客户端说自己在这个位置，服务端就接受。理论上客户端可以穿墙。朋友服无所谓，公开服等于送挂。

**三、命中判定、交互距离跟着变成客户端驱动。**
`Combat:CanHitTarget` 用的是服务端位置，现在服务端位置等于客户端上报值。攻击距离不再由服务端说了算。

## 怎么验证有没有生效

把配置里的 **记录被丢弃的上报** 打开，然后看 `server_log.txt`，每 10 秒会有一行：

```
[CA] 10s: accepted=61 rejected=2 (3.2% rejected)
```

- **拒绝率低于 5%** → 服务端基本在跟着你走，对账已经抹平了。
- **拒绝率 10% 以上** → 先看是不是加速 buff（走路速度变快、`slack` 还是 2.0）。不是的话把 `slack` 调到 3.0。
- **`accepted` 一直是 0** → 包根本没到，检查服务器有没有装、配置有没有开。
- **日志里 `reject streak=` 一路涨到几十** → 客户端和服务端已经分叉，通常意味着 `max_step` 之外的某条闸门没拆干净，或者玩家在骑乘状态。

体感上还有两个自检：

1. 边走边砍树，如果能在挥砍动作里继续移动，说明「客户端始终预测」这一半生效了。
2. 在 100ms 延迟下按住方向键，如果角色不再先原地踏步再窜出去，说明对账这一半生效了。

两个都对，才算成了。只对一个，等于没做。

## 已知不确定（没有实机验证过）

1. **`locomotor` 这一层没有 busy 闸门。** 查过 `_ref/scripts-2026/components/locomotor.lua`：`WalkInDirection` 直接设 `wantstomoveforward` 并推 `locomote` 事件，不检查 busy；只有转向（`FaceMovePoint`、`SetMoveDir`）会因为 busy 跳过。所以强制 `CanLocomote` 之后客户端**会**开始移动。剩下不确定的是 `SGwilson` 在 busy 状态里是否接受 `locomote` 事件——那决定动画会不会切到走路，但不决定位置。
2. 每帧调用 `Transform:SetPosition` 对 `locomotor` 内部状态（`dest`、`onreachdestination` 事件）的影响未知，可能出现偶发的动画重置。
3. 服务端下发的权威位置仍然是延迟的（至少 RTT/2）。客户端会不会因此仍触发一次小纠正，只能实测。
4. 静默窗口靠「服务端位置突变 + 状态机不在 `moving`」推断。如果传送发生时状态机还挂着 `moving` 标签（比如边走边被传送），推断会失效，旧包仍可能把玩家拽回去一次。
5. `no_pause` 会连带屏蔽 `stun_frames` 那几次暂停（约 7 帧 = 0.23 秒）。被击晕时客户端会多预测一小段，然后由位置对账拉回。

## 和原版比，理论上好在哪

原版的问题不是延迟高，是**预测会被整段关掉**：`CanLocomote()` 一关，输入延迟就退回整整一个 RTT，而且关得非常频繁。这个模组做两件事——把闸门拆掉（客户端始终算），把对账抹平（服务端跟着客户端）。两件都成立，才会接近 Minecraft 的手感。

只做其中一件，大概率没感觉。
